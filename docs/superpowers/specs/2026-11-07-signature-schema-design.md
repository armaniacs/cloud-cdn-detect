# 署名DBスキーマ化・フィード追従 設計メモ (2026-11-07)

Task 9 Step 1 の成果物。方針決定済み、実装は Task 10 以降。

## 決定事項

1. **メンテ体制**: 外部PRを積極受入 → CI検証 (スキーマ・境界テスト) に投資する
2. **自動化の範囲**: 変更検知・通知のみ。週次でフィード鮮度・URL有効性をチェックし、差分があれば Issue/PR を下書き。取込判断は人間
3. **YAML化**: 全面移行を最終形とするが、**段階移行** (Emerging 等 → 既存表の順に分割PR、目視レビュー可能サイズ)
4. **Markdownの扱い**: **ハイブリッド**。解説・運用ルールは人間編集、表・フィード index 部のみ生成。差分可読性を残す

## 深掘りセッション — 2026-11-07

### 挑戦した仮定
| 仮定 | リスク | 発見 | 決定 |
|---|---|---|---|
| H1: YAML化すれば運用性が上がる | 高 | 一人目視で足りる間は二重管理コストが上回る。外部PR受入を前提にすればCI検証の利益が成立 | 外部PR受入＋段階移行＋ハイブリッドで実行 |
| H2: 全量追従で網羅最大 | 高 | 変わるのは主要フィードのみ (AWS daily/Azure weekly)。Baidu/Tencent静的CIDRは不変で取込効果薄 | 変更検知・通知のみに縮小 |
| H3: 自動化の運用コストを払える | 高 | 全量同期は肥大・誤混入リスク。通知のみなら週次Workflow＋人間判断で維持可能 | 同上 |
| M1: 重み 35/25/… に客観性 | 中 | w4f経験則の借用で検証データなし。偽の客観性の恐れ | 重みは目安扱い、証拠表の行単位記録を正本に残す |
| M2: 全フィード同列追跡が必要 | 中 | Unknown の害＜偽陽性の害。境界規則・フィードなし明記の方が価値高 | Tier別: 主要6＋Gcore を通知対象、静的CIDR群は変更時のみ |

### 新たに発見したリスク
- 全面移行の一気PRはレビュー不能化 → 段階移行で回避 (決定済み)
- 生成物混在で「どこを編集すべきか」迷子化 → ハイブリッド＋生成区間の明示マーカーで回避
- 通知Workflowの放置 (誰も見ない通知) → Issue自動作成＋ラベル付けで可視化

### 未解決の疑問

- YAML分割単位 (プロバイダ毎ファイルか、サービス毎か) — 決定: プロバイダ毎ファイル (Task 10)
